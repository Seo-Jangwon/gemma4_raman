# Raman Agent Benchmark — Verification Design

How a task is decided correct or incorrect.

- Scope: 143 tasks, 303 nominal points, run against **real hardware** through a live server.
- Tool surface: 49 tools for AILA (45 hardware + 3 attachment + 1 KB), 53 for CoALA (+4 memory actions).
- Companion document: `벤치마크_구성.md` describes *what the benchmark is made of*; this file
  describes *how it decides an answer is right*.

---

## 1. The verdict is binary

Since 2026-08-03 a task has exactly one of four outcomes. There is no partial credit.

| Outcome | Meaning |
|---|---|
| `pass` | every gradable check passed |
| `fail` | at least one gradable check failed |
| `blocked` | every check was ungradable (instrument cannot cover what the task needs) |
| `error` | the run itself failed (infrastructure, empty LLM reply) — no answer was ever received |

```
solve_rate = pass / (pass + fail)
```

`blocked` and `error` are excluded from the denominator. Recording a setup mistake or an
instrument accident as agent incompetence is the worst failure mode this framework can have, so
those two categories are kept structurally separate from `fail`.

**Why binary.** Weighted partial credit hid defects. A bug in `plan_order` that demanded a step
the prompt never mentioned gave T063 1.91/3 (64%), which read as "mostly right" and nobody
investigated. Binary turns that into 0 and makes it loud.

The cost of binary is that a single over-strict check kills the whole task, so **every check must
test only what the prompt actually demanded** — nothing inferred, nothing stylistic.

> **Implementation note.** `Check.weight`, `Check.score` and `partial=True` are no longer read by
> the report layer. 134 `weight=` and 7 `partial=True` occurrences remain in the task files and are
> inert. `bench/check.py`'s module docstring still documents the retired weighted formula.

## 2. Two tiers of evidence

Array similarity alone cannot grade everything. Measured on a real polystyrene reference with a
fluorescence background added and removed by IPBSA:

| Candidate | cosine | NRMSE |
|---|---|---|
| IPBSA order 5, iterations 100 → 300 (legitimate implementation difference) | 1.0000 | 0.0000 |
| IPBSA order 5, convergence 1e-3 → 1e-4 (legitimate implementation difference) | 1.0000 | 0.0007 |
| **IPBSA order 4 (wrong order)** | **0.9999** | **0.0014** |
| **IPBSA order 6 (wrong order)** | **1.0000** | **0.0009** |
| Plain polyfit order 5 (wrong algorithm family) | 0.9259 | 0.0417 |

IPBSA is iterative clipping, so orders 4/5/6 converge to effectively the same curve. **Whether
`poly_order=5` was honoured cannot be recovered from the output array.** The algorithm *family*,
by contrast, separates cleanly.

Hence two tiers:

- **Tier 1 — procedure.** Was the instruction actually applied? Tool arguments, call order, call
  counts, instrument state before/after. Catches what arrays cannot.
- **Tier 2 — result.** Is the output the right answer? Values, arrays, labels, sets.

The two tiers are a division of labour, not redundancy.

> **Known gap.** Tier 1 only exists where the parameter crosses a tool boundary. For tasks that
> operate on an uploaded CSV (T039, T040, T041, T042, T047), the agent writes its own code inside
> `run_analysis`, so `poly_order` never appears as a tool argument — and per the table above the
> array cannot distinguish it either. For those tasks the stated order requirement is
> **unverifiable by construction**; only the algorithm family is actually tested. T059 is the
> counter-example: it corrects a *measured* spectrum via `apply_background_subtraction`, so
> `chk.arg(run, "apply_background_subtraction", "poly_order", 5)` genuinely applies.

## 3. Check primitives

Every check returns one `Check`. `bench/check.py` holds them all.

| Primitive | Tests |
|---|---|
| `chk.near` | scalar within absolute `tol` or relative `rel` (default 5%) |
| `chk.equals` | exact label / material / index match, case- and space-normalised |
| `chk.relation` / `chk.increasing` | ordering relations that hold regardless of sample (SNR rose, sign, monotonicity) |
| `chk.state` / `chk.delta` / `chk.unchanged` | instrument state read back from the device |
| `chk.called` / `chk.arg` / `chk.arg_set` / `chk.arg_not` / `chk.order` | tool calls, their arguments and their sequence |
| `chk.keywords` | free-text answer contains a term only someone who understood the task would use |
| `chk.reported` / `chk.reported_label` | the agent *reported* the value — structured JSON first, prose fallback |
| `chk.set_match` | set equality with 1:1 matching inside `tol`; `ordered=True` also fixes position |
| `chk.array` | array comparison, see §4 |
| `chk.plan_order` | plan-only tasks: are the GT steps present in order (extra steps forgiven) |
| `chk.blocked` | the check could not be run at all — excluded, not failed |

Default tolerances:

```
stage coordinate   1e-4 mm        grid coordinate     1e-3 mm
peak position      3 cm-1         scalar relative     5%
exposure           1e-3 s         array (exact)       rtol 1e-6
```

Exposure deserves a note: the CCD quantises to its own clock, so commanding 1.0 s reads back as
1.00002 s. An earlier `tol=1e-6` made a *correctly executed* T016 fail deterministically. The
tolerance is 50× the observed error — loose enough to accept the hardware, tight enough that 0.5 s
and 1.0 s remain distinguishable.

## 4. Array comparison and its thresholds

```
cos   = a·b / (|a||b|)                     # shape
NRMSE = RMSE(a, b) / (max(GT) - min(GT))   # magnitude
```

| Transform class | Criterion | Rationale |
|---|---|---|
| Deterministic (Savitzky-Golay, derivative, normalisation, slicing, averaging) | `rtol 1e-6` | one correct implementation exists; no reason to tolerate error |
| Algorithmically free (baseline removal, spike removal) | `cos ≥ 0.99` **AND** `NRMSE ≤ 0.02` | admits the legitimate variants (≈1.0000 / 0.001), rejects the wrong algorithm (0.9259 / 0.0417) |

The commonly used 0.95 cosine threshold has **no discriminating power in this domain**: adjacent
spectral points are highly correlated, so cosine starts high and even wrong-order answers score
0.9878–0.9999.

The two conditions are ANDed because cosine alone misses a scale error and NRMSE alone misses a
shape error.

For `mode="exact"`, `atol` is scaled to the data (`max|GT| × 1e-6`, floored at 1e-9). A fixed
1e-9 rejected *correct* answers on operations whose result sits near zero — subtraction and
averaging in particular, where the CSV's six-decimal round trip costs up to 5e-7.

**Parameters such as polynomial order and window length are not recoverable at this tier.** See
the gap noted in §2.

## 5. Where ground truth comes from

Three sources, in order of strength.

### 5.1 Precomputed GT — deterministic function of a shipped input file

The task ships a CSV/PNG under `benchmark/inputs/`, and the answer is a fixed function of it.
Written directly into the task file. Verified by independent recomputation:

| Task | Protocol | Recomputed | Declared GT |
|---|---|---|---|
| T043 | `find_peaks(prominence = 5% of range)` → 9 peaks → 7 largest by prominence → ascending | `[620, 793, 1001, 1031, 1154, 1450, 1602]` | identical |
| T044 | same detection → 3 largest by intensity | `1001 / 1602 / 1031` | identical |
| T050 | `max(990–1012) / std(1800–1900, ddof=1)` | `158.99277` | `158.99277` |

Reference arrays for multi-step pipelines live in `benchmark/gt/arrays/*.csv` (13 files) and are
loaded by the 13 tasks that need them.

**This only works when the task states the computation protocol.** Signal and noise windows, ddof,
peak prominence, interpolation-then-normalisation order — all are written into the prompt. Without
them the grader and the agent compute different correct answers.

> **Fragility to watch.** T043's 7th and 8th peaks differ by 5% in prominence (117.2 vs 111.5).
> Any change to the input file or to the prominence convention flips the answer set. Pin it.

### 5.2 Post-hoc GT — recomputed from what the agent measured

Absolute values from live hardware depend on the sample, the alignment and the day, so they cannot
be written down in advance. But **a function of the agent's own saved files is deterministic**:

```
agent   : measure → save → analyse → report
grader  : re-read those files → recompute by the stated protocol → compare with the report
```

The mean of five measurements is fixed by those five files; the cosine distance between two
spectra is fixed by those two. `bench/spectra.py` is the single place those protocols are written
(SNR windows, peak prominence, common-axis interpolation, RSD, saturation count).

Applied by 15 tasks: T058–T062, T064, T067–T071, T077, T100, T102, T110.

> **What this does and does not prove.** Post-hoc GT verifies that the agent's *report is
> consistent with its own output*. It does not verify that the output is correct. An agent that
> saves a badly processed array and then reports metrics faithfully derived from it will pass.
> Tasks in this class should therefore always be paired with a tier-1 procedure check or a
> relation check that constrains how the array was produced.

> **Defect — T059.** The task says "report the peaks found", but the GT is
> `sp.peaks(x, y)[:5]` — the five *lowest-wavenumber* peaks. `set_match` requires equal
> cardinality, so an agent that correctly reports all peaks fails on count. Either the prompt must
> ask for five, or the truncation must go.

### 5.3 Relational GT — the improvement, not the value

Where no absolute value can be fixed, the task grades a *relation* that holds for any sample:
autofocus raises SNR, a saturated setting must move downward, the final measurement must contain
zero saturated pixels. Used by the troubleshooting tasks. Robust to whatever sample is loaded.

## 6. Making the run gradable

### 6.1 Answer contract

Grading a value out of prose can only ask "is a number near the expected one somewhere in the
text", which passes on coincidence. So the harness appends the same JSON output contract to every
prompt, and each task declares the exact key names and shapes it will read:

```python
answer_keys=[("peaks", "list of 3 numbers - peak positions in cm-1, ordered by "
                       "descending intensity. Numbers only, not objects")]
```

The harness — not the agent prompt — attaches this, so the two architectures always receive the
identical instruction in the identical position.

`run_all.py --check` cross-checks the declared keys against the keys `evaluate()` actually reads
and refuses to run on a mismatch. This closes a whole class of silent zeros: T044 once produced
the exactly correct `[1001, 1602, 1031]` and scored 0 because it named the key
`highest_intensity_peaks`; T126 identified all five materials and scored 0 for keying on filenames.
Shapes are declared for the same reason — T043 answered `[{"position": 620.0, ...}]` where the
grader expected `[620.0, ...]` and lost all 7 checks.

### 6.2 Preflight

Before any task runs:

- the server is reachable and holds the instrument;
- the **bench copy** of the agent module is loaded (`single_agent_*_bench.py`). The bench copy
  differs from production in exactly one place: an empty model reply is raised as `error` instead
  of being passed through as the final answer, so a context overflow is not scored as a wrong
  answer. Running the production module instead is a fatal preflight failure;
- the instrument's wavenumber axis is read, and every task that declared `windows` is tested
  against it. A task whose grading window the axis cannot cover is marked `blocked`, not `fail`.

### 6.3 Isolation between tasks

Instrument state is process-global and does not revert. If T102 leaves the exposure at 2.0 s, the
next task starts there — **task order would change the score**. `bench_ops.reset_all()` runs before
and after every task and restores laser, cooler, target temperature, exposure, shutter, acquisition
mode, read mode, trigger, preamp gain, shift speeds, image flip, stage speed and camera to
`DEFAULTS`.

The stage is homed to `(37.8759, 25.24805, 0.0)` — the registered safe waiting position, not the
computed geometric centre.

**Order is the whole of the safety here: retract Z to 0 first, then move X/Y.** Reversed, the
stage sweeps tens of millimetres at sample height and can destroy the objective or the sample. If
the current coordinate cannot be read, the Z retraction is impossible, so that step is reported as
failed and skipped — the harness never moves X/Y to an arbitrary position.

As a side effect the relative-coordinate tasks (T002, T031, T036, T064, T070, T110 — "+0.1 mm from
here") always start from the same place, which is what makes them reproducible.

CoALA's long-term memory lives on disk and survives a reset. It must be isolated with
`RAMAN_MEMORY_SCOPE=session`, otherwise task N is solved with the accumulated experience of tasks
1..N-1 and task order silently changes the conditions.

### 6.4 Reproducing conditions safely

The test is always: *can this state be produced on the real instrument without damage?*

| Mechanism | Used for | Why it is safe |
|---|---|---|
| `b.hw(tool, ...)` | pre-setting exposure, cooler, focus offset (6 tasks: T079, T090, T093, T099, T100, T102) | ordinary tool calls, tracked so a silently failed setup is recorded rather than blamed on the agent |
| `b.hold_busy(s)` | contention / "instrument busy" (T090) | takes `instrument_guard` in a side thread; the laser never fires |
| `b.inject_scene(png)` | synthetic microscope scene | patches **`analyze_microscope_image` only**. Replacing the camera frame itself would also freeze autofocus and grid spot detection — sharpness would stop varying with Z and autofocus would never converge |
| `mode="hypothetical"` | states that cannot be produced safely at all | the agent plans instead of acting; graded with `chk.plan_order` |

Saturation is reproduced by **raising exposure only**. Raising power could burn the sample and is
not needed.

## 7. Known limitations

1. **The vision axis has no live measurement.** All three vision tasks (T037, T063, T076) are
   `hypothetical`. The vision solve rate therefore measures whether the agent can *describe*
   locating a target, not whether it can locate one. Two diagnostics tasks (T107, T111) are in the
   same position.

2. **Post-hoc GT measures consistency, not correctness** (§5.2).

3. **Infrastructure warnings are promoted to `error` and leave the denominator.** `run.errors`
   mixes fatal conditions (stream failure, empty reply) with advisory ones (`reset warning: …`,
   `setup did not take effect …`, `could not read the starting state`). Verified: a task with
   every check passing plus one benign reset warning reports `error`, not `pass`. The solve rate's
   denominator is thus sensitive to instrument noise. Advisory warnings should be carried in a
   separate field.

4. **Ungraded parts of prompts.** T128 asks for a `spectrum_id` tie-break but only the material is
   checked. T043 asks for intensities alongside positions but only positions are declared and
   graded. Asking for something ungraded costs the agent tokens and buys no signal.

5. **T044 grades order-insensitively** although the prompt, the `criteria` string and the
   `answer_keys` description all demand descending-intensity order. Verified: all six permutations
   of the correct three peaks pass. `ordered=True` is missing.

6. **Two ground-truth stores.** `benchmark/gt/*.json` (144 files plus `manifest.json`) is read by
   nothing on the grading path — only by `generate/apply_hypothetical.py`. The live GT is inlined
   in `tasks/*.py`, with `gt/arrays/*.csv` as the only live part of `gt/`. The JSON store can drift
   from the tasks without any signal; `gt/T091.json` is already orphaned with no matching task.

7. **`criteria` strings that describe retired behaviour.** T122 and T126 still promise partial
   credit, which binary grading cannot give.

## 8. Capability axes

One axis per task, used only for aggregation.

| Axis | Measures | Tasks |
|---|---|---|
| procedure | chaining several tools in the right order with the right arguments | 30 |
| instrument control | putting the commanded coordinate/setting onto the device | 28 |
| data processing | transforming and computing on a signal in code | 27 |
| safety | refusing, reporting limits, not doing what must not be done | 23 |
| identification | deciding material or state from a spectrum | 21 |
| diagnostics | narrowing a symptom to a cause and acting | 11 (9 live) |
| vision | reading the camera image to decide a position | 3 (0 live) |

Nominal weights (1 point single-step, 2 points sequence/preprocessing/safety/matching, 3 points
acquisition+analysis/troubleshooting) total 303, but the binary verdict does not use them; they
remain as a difficulty label.
