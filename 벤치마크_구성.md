# Raman Agent Benchmark — Composition

What the benchmark is made of and how a run proceeds.

Companion document: `벤치마크_채점설계.md` describes *how correctness is decided*; this file
describes *what exists and how it fits together*.

---

## 1. What is being measured

Two single-agent architectures drive the same real Raman spectrometer through the same tool set.
The only independent variable is orchestration.

| | AILA | CoALA |
|---|---|---|
| Orchestration | stateless ReAct — one LLM call may emit many tool calls, all executed | explicit decision cycle: planning (retrieval, repeatable) → evaluate → select → execute one commit action |
| LLM layer | `ChatOllama(gemma4)` + `bind_tools` + manual loop | identical model, identical host, identical binding |
| Long-term memory | none | episodic (`experiences.json`) + semantic (`insights.json`) |
| Bound tools | 49 = 45 hardware + 3 attachment + 1 KB search | 53 = the same 48 + 5 memory actions |
| Step budget | 100 LLM iterations | 150 cycles / 150 propose calls / 6 planning rounds per cycle |

Capability parity is enforced structurally, not by convention: both agents import the *same list
object* `FILE_TOOLS` and the *same* `RAMAN_TOOLS`, and both search the knowledge base through the
same `knowledge.search_kb`. They never import each other — shared upper dependencies
(`safety_limits`, `run_store`, `detail_log`, `knowledge`) are neutral utilities, so the
independence of the comparison holds.

Both are graded through the **bench copies** (`single_agent_AILA_bench.py`,
`single_agent_CoALA_bench.py`), which differ from production in exactly one behaviour: an empty
model reply becomes an `error` event instead of being returned as the final answer. Preflight
refuses to run against the production modules.

## 2. Layout

```
benchmark/
  run_all.py            runs every task and aggregates the result
  bench/                shared parts the task files use
    task.py               Task      — the task definition (prompt, score, inputs, answer keys)
    client.py             Bench     — the channel to the instrument-owning server
                          Run       — one execution record (calls, text, answer, artifacts, state)
    check.py              chk       — check primitives; each returns one Check
    spectra.py                      — reads saved spectra; the single place recomputation
                                      protocols are written (SNR, peaks, cosine, RSD, saturation)
    answer.py             A         — pulls values out of the agent's JSON, absorbing shape variance
    report.py                       — writes <TASK>.json, summary.json, SUMMARY.md
    tools.py                        — tool name / parameter table, for typo detection
  tasks/                T001.py … N15.py — 143 files, one per task
  inputs/               74 shipped input files (csv, png)
  gt/arrays/            13 reference arrays for multi-step pipelines
  gt/*.json             legacy per-task GT manifests — not on the grading path (see §7)
  generate/             dataset and reference-library generators
backend/
  bench_ops.py          instrument control for the benchmark, running inside the server process
  server.py             /api/bench/* endpoints
results/<run_id>/       <TASK>.json per task + summary.json + SUMMARY.md
```

**One task = one file.** Before 2026-08-03 a single task's definition was spread over five places
(the xlsx prose, `gt/manifest.json`, `grader/specs.py`, `grader/posthoc.py`, `grader/grade.py`).
Understanding T062 meant opening all five, and fixing it meant they could diverge. Now
`tasks/T062.py` is the whole story.

## 3. Anatomy of a task file

Three things, and nothing else:

```python
TASK = Task(
    id="T044",                    # must equal the filename
    score=2,                      # difficulty label
    axis="data processing",       # aggregation axis
    mode="live",                  # or "hypothetical"
    inputs=["T044.csv"],          # uploaded before the run
    windows=[("SNR signal window", 990.0, 1012.0, 3)],   # axis coverage this task needs
    criteria="SET(ordered 3 items, ±3 cm-1)",            # one line, English, copied into the result
    prompt="In T044.csv, report the positions of the 3 highest-intensity peaks …",
    answer_keys=[("peaks", "list of 3 numbers - peak positions in cm-1, ordered by "
                           "descending intensity. Numbers only, not objects")],
    enforce_grid_gate=False,
)

def setup(b):            # optional — the state this task requires
    b.hw("set_ccd_exposure", exposure_time=5.0)

def evaluate(b, run):    # required — this list of Checks is the score
    return [chk.set_match("peak positions", run.answer.get("peaks"),
                          [1001.0, 1602.0, 1031.0], tol=TOL_PEAK_CM1)]
```

`Task.__post_init__` rejects an empty prompt, a non-positive score, an empty `criteria`, an
invalid `mode`, and malformed `answer_keys`. A result file must be self-explanatory, which is why
`criteria` cannot be blank.

### Field notes

- **`criteria`** is written in English because the result JSON is consumed by scripts, tables and
  outside collaborators. Korean in filenames or payloads breaks on cp949 hosts.
- **`windows`** declares the wavenumber intervals the grading needs. The instrument axis is set by
  the equipment PC's `Config.ini`; if the configuration cannot cover a window, the task is
  `blocked`, not failed.
- **`answer_keys`** is what makes value grading possible at all — see §5.
- **`enforce_grid_gate`** turns the human-approval interlock back on. Default off, because with no
  human in the loop every grid scan would be refused and the run would stall. It is enabled only
  for the two tasks where refusal *is* the correct answer (N01, T028).
- **`mode="hypothetical"`** means the agent must plan rather than act. Used where the state cannot
  be produced safely on the real instrument (T037, T063, T076, T107, T111). Setup is skipped for
  these — pre-setting would contradict the premise.

## 4. Execution flow

The instrument DLLs and the laser COM port can be held by **one process only**. The server takes
those handles in its lifespan hook, so the harness cannot touch the hardware directly — it drives
the server over HTTP. That also means the benchmark can run with the front end open, watching live
state, and the DLLs are never opened twice.

Per task:

```
reset()            everything back to DEFAULTS, whatever the previous task left behind
upload(inputs)     shipped input files placed where the agent can see them
setup(b)           the state this task requires   (live mode only)
state()            starting snapshot — taken AFTER setup, so what changed is the agent's doing
run(task)          agent executes; SSE events are collected into Run
state()            ending snapshot
evaluate(b, run)   the task file returns its list of Checks
teardown(); reset() release locks and tool patches, restore DEFAULTS
```

Server endpoints used: `/api/bench/reset`, `/tool`, `/scene`, `/busy`, `/inputs`, `/state`,
`/artifacts`, `/preflight`, `/teardown`, `/stream`.

The session id is `bench_<run_id>_<agent>_<task>_<hex6>`, which makes every artifact directory
(`data/runs/<label>/`) and every detail log self-identifying by task and agent.

### Preflight, before anything runs

1. server reachable;
2. the loaded agent module is a bench copy — otherwise fatal;
3. the wavenumber axis is read and every declared `window` is tested against it; tasks the axis
   cannot serve are announced up front and their checks become `blocked`.

### Static check without hardware

```
python benchmark/run_all.py --check
```

verifies, for all 143 files: the `TASK`/`evaluate` contract, id matching the filename, at least one
check per task, tool names and `setup` argument names against the real schema, presence of every
declared input file, and — most importantly — that the keys `evaluate()` reads are exactly the keys
`answer_keys` declares. Current status: clean, 143 tasks, 303 nominal points.

## 5. The output contract

Every prompt gets the same JSON block appended, by the harness rather than by either agent prompt,
so both architectures receive the identical instruction in the identical position:

```
When you are done, end your reply with a JSON block holding the values you were asked to
report, like this:

```json
{"key": value, ...}
```

The JSON block must include these keys, spelled exactly like this, with the shape described
for each:
  "peaks": list of 3 numbers - peak positions in cm-1, ordered by descending intensity.
           Numbers only, not objects

Give plain JSON numbers and strings - no units, no LaTeX, no thousands separators. If the
task asked you to refuse, explain, or ask a question instead of measuring, say so in plain
text and omit the block.
```

`bench/answer.py` absorbs shape variation on the way back in — a ranking may arrive as a list of
objects, a list of ids, or parallel arrays — but it never guesses a missing value. A key that
cannot be found returns `None` and the check records "not reported".

## 6. Data assets

| Asset | Count | Produced by |
|---|---|---|
| Input spectra / images (`inputs/`) | 74 | `generate/make_dataset.py` on top of `generate/synth.py` |
| Reference arrays (`gt/arrays/`) | 13 | same generator, same run |
| Reference libraries | `reference_library.csv` (6 materials / 12 spectra), `reference_library_8.csv` (8 spectra) | `generate/make_library.py`, band definitions in `generate/materials.py` |

The generator writes the input file and its ground truth **in the same pass**, so they cannot
diverge. `generate/verify_dataset.py` then confirms the generated data actually makes the task
solvable — for the identification tasks in particular, that the intended material is genuinely
separable from its distractors (PET vs PMMA, calcite vs aragonite).

`generate/sync_uploads.py` copies `inputs/` into `data/uploads/<date>/` so the agent's
`list_uploaded_files` can see them.

## 7. Ground-truth stores

| Store | Read by grading? | Contents |
|---|---|---|
| Values inlined in `tasks/*.py` | **yes** | scalars, peak sets, labels, orderings |
| `gt/arrays/*.csv` | **yes** | 13 reference arrays for multi-step pipelines |
| `gt/*.json` (144 + `manifest.json`) | **no** | legacy per-task manifests; only `generate/apply_hypothetical.py` still reads them |

The JSON store is a leftover from the pre-2026-08-03 architecture. It is not wrong — spot checks
agree with the task files — but it is a second copy that can drift silently, and `gt/T091.json`
is already orphaned with no matching task. It should either be regenerated as the source the task
files are built from, or deleted with `gt/arrays/` kept.

Special mechanisms in use:

| Mechanism | Tasks |
|---|---|
| shipped input files | 74 files across the data-processing, matching and diagnostics tasks |
| `setup(b)` pre-conditioning | T079, T090, T093, T099, T100, T102 |
| `windows` axis requirement | 11 |
| `enforce_grid_gate=True` | N01, T028 |
| `mode="hypothetical"` | T037, T063, T076, T107, T111 |
| post-hoc recomputation | T058–T062, T064, T067–T071, T077, T100, T102, T110 |

Troubleshooting is split by how the symptom can be produced:

- **file-diagnosis** — the symptom is baked into a shipped CSV. No hardware needed, fully
  deterministic GT (T098, T101, T103, T105, T106, T108, T112).
- **pre-conditioned** — the symptom is created safely by `setup(b)`: exposure raised until
  saturation, Z detuned by 0.05 mm, exposure dropped to 0.05 s. Graded on the before/after
  relation, so any sample works (T099, T100, T102).
- **plan-only** — overheating or a broken stage cannot be produced without risking the instrument.
  The premise stays in prose and the plan is graded (T107, T111).

## 9. Reading a result

`results/<run_id>/<TASK>.json` carries everything needed to reconstruct the verdict without
re-running:

```
question / criteria            what was asked, and what counts as right
result / reason                pass | fail | blocked | error, and the first failing check
checks                         every check with expected value, observed value, kind
failures                       only the ones that failed
answer_text / answer_json      what the agent actually said
tool_calls                     name, arguments, ok flag, in order
artifacts                      files the agent saved
state_before / state_after     instrument snapshots — without these a state failure is unauditable
session_id / elapsed_s / errors
```

`summary.json` and `SUMMARY.md` aggregate: solve rate over gradable tasks, per-axis breakdown,
per-task table, and an explicit list of everything excluded from the denominator (`blocked`,
`error`, `not_run`). The console summary is Korean; every file is English.

## 10. Running it

```bash
# terminal 1 — the process that owns the instrument
python -m backend.server

# terminal 2
python benchmark/run_all.py --agent AILA
python benchmark/run_all.py --agent CoALA --tasks T001,T062
python benchmark/run_all.py --check                 # static check, no hardware
```

Environment worth setting for a comparison run:

| Variable | Purpose |
|---|---|
| `RAMAN_AUTONOMOUS=1` (default) | no human is available; a turn that ends in a question is a failure |
| `RAMAN_MEMORY_SCOPE=session` | isolates CoALA's long-term memory per task, so task order cannot change the conditions |
| `RAMAN_EPISODIC_MEMORY=0` | ablation — removes episodic memory while leaving semantic memory intact |
| `RAMAN_LLM_TIMEOUT_S` (default 600) | wall-clock guard; the step counter alone cannot catch a hung HTTP call |
